## Summary

This is the first full audit, the security and privacy part of the sweep before 1.0. All seven lanes ran on the 1.0 candidate, with bug, redundancy and efficiency audits beside them. Every finding rated Low or above went to a separate verifier, and a second reviewer checked the triage. Nothing was rated Critical or High. Three findings were Medium. Two were in the release path's repository settings: code-owner review was not enforced on `main` (F-01), and a release created under a tag outside `v*` could have taken over the installer one-liner (F-06). The third was a bug: `fil -N` asked the install question (BUGS-1). All three are fixed in 1.0.0. F-01 was a setting with nothing to patch, and no released version was affected by F-06 or BUGS-1, so no advisory was needed. Five of the ten Low findings were documents that overstated what the code does; they now say what it does. A clean report is evidence, not proof.

## Scope

A full audit runs every lane on the whole tree (`docs/audits/README.md`, "Path to lane"; the briefs are in [`LANES.md`](LANES.md)):

- **A**, wire and parsers: `fil-proto`, the golden encoding and its frozen lines, `fil-term`'s input, the bootstrap's answer parser, every fuzz target.
- **B**, transport, auth and keys: the ssh pipe, direct QUIC, the per-attach keys and their registry, certificate pinning, the dialer and consent.
- **C**, daemon, sessions, policy, bootstrap and upload: the socket directory and peer-UID checks, the relay and `Route`, sessions, the server policy, the management commands, the install path and its garbage collection.
- **D**, forwarding, SOCKS, agent: `-L`, `-R` and `-D`, `remote_peers = "same-user"`, `fil ports`, the agent filter and relay.
- **E**, prediction secrets: `fil-predict`, the client's engine, the daemon's echo acknowledgments.
- **F**, supply chain and release: `Cargo.lock`, `deny.toml`, the pins, the GitHub workflows and the live repository rulesets (read-only), `tests/release/`, `packaging/` (the installer, Homebrew, AUR), the apt and dnf repositories, CODEOWNERS.
- **G**, privacy and claims: every log macro at info and above in the non-test code (about 130 call sites) and the debug ones that carry fields, the offline-input log, the QUIC identity, `Attach`'s fields, `fil --version`, the jobs and version fields; and the claims in `README.md`, `docs/user/`, `SECURITY.md`, `DESIGN.md` §9, §11 and §11.1, and `fil.1`.

The bugs audit covered the 1.0 additions (`fil -N`, the per-build daemons, `Route`, `fil kill --outdated`) and re-checked earlier review findings; the redundancy and efficiency audit covered the whole tree and CI.

### Out of scope, and why

- The non-goals in `SECURITY.md` "Scope": root on the host, a compromised client machine, the terminal emulator's own escape handling, keystroke timing, and the four predictive-echo residuals as documented. They were considered and not reported.
- Real hardware and real networks: the audit read the code and ran local probes; the real-network and arm64 harnesses are CI suites, not part of the audit.
- GitHub itself, and the settings that only an admin can read (see F-01's notes).

**Not a finding** (considered and left alone):

- Same-uid processes on the host reaching the daemon socket, the lending socket, `Route` or `fil forward` requests: by design the daemon serves one user, and the client's consent is the boundary for what a host process can make the laptop do.
- Other users on the host reaching `-R` ports on loopback with `remote_peers = "any"`: documented.
- Policy bypass by a user with a shell: the policy is a courtesy, not a boundary (`DESIGN.md` §11.2).
- On macOS, a fork at the instant a lent descriptor arrives can hold the wire lock a little longer (no `MSG_CMSG_CLOEXEC`): documented in `lend.rs`; same user, no security effect.
- A second agent session-bind appended by the host: the first hop is always the run's random bind key, so a destination-constrained key still fails the hop check.
- The host learns the laptop's short host name by default (the takeover label): documented and configurable.
- An on-path observer can tell a direct connection is fil (SNI `fil.invalid`, ALPN `fil/1`), and other users on the host can see `fil server --stdio` and the bootstrap in `ps`: neither is claimed hidden.

## Method

- **Models.** Claude Opus 5.5 for every role, as the runbook asks for a baseline: one reviewer for lanes A to D, one for lanes E to G, one each for bugs and for redundancy and efficiency; a verifier, a separate agent that saw each finding's claim and code but not the lane's reasoning and wrote its own probes; and a second reviewer for the triage, who wrote neither a lane report nor the verification. Each fix PR then had its own independent review, with a re-check of its fixes.
- **Pinned.** `bcd8460`, read in a read-only worktree; probes ran in throwaway copies of the same commit, never in the repository.
- **Tools.** rustc 1.99.1 (`rust-toolchain.toml`), cargo-deny 0.20.2, cargo-fuzz 0.13.2 on the nightly toolchain, on Apple silicon. osv-scanner was not installed, so the same query went to the OSV API (`querybatch`) for all 254 registry packages of `Cargo.lock` and `tests/terminals/exporter/Cargo.lock`, on 2026-11-15.
- **Run.**
  - `cargo deny --locked check advisories licenses bans sources`: all ok.
  - `cargo test -p fil-predict --tests` (all pass; the mutants are on demand), `cargo test -p fil-client --lib offline`, `cargo test -p fil-daemon --lib logging`.
  - `lint-workflow.sh` on every workflow, `recipes.sh`, `audit-age.sh`.
  - Probes against real binaries and private daemons: the QUIC listener with an empty key registry (B-01), the relay's hello reader (A-01), the overlay with short reads (E-01), `fil --version` from a copy under the home directory (G-04), `fil -N` with a fake `ssh` in a pty and as a background job (BUGS-1), a tunnel taking over a sized session (BUGS-2), and `client.log` at the default level after a failed attach.
  - Read-only GitHub API calls: the rulesets, the collaborators, the workflow states, the releases and each action's latest tag.
- **Fuzzing** (DESIGN.md §12: before a release, each target for a parser of peer or remote-host input for 5 minutes; the config-file targets only when their parser changes). The eleven targets below ran on the pinned commit with `-timeout=20` and `-max_len=17000` (70000 for `preamble`), seed corpora plus a fresh corpus, two targets at a time. No crash, hang or out-of-memory in any.

### F-01 (Medium): code-owner review was not enforced on `main`

- **Claim it broke.** `docs/m4/release.md` §9.2 (the release key reaches `.github/release-signers` through a code owner's review), the CODEOWNERS header, and the trust root of `release-verify`, which reads the signers from `main`. CODEOWNERS listed the right files, but the `main` ruleset did not require a code owner's review, so it enforced nothing.
- **Who, with what access.** Anyone with write access to the repository, or a stolen token of such an account. Not a user, not a network attacker.
- **Evidence.** The live `main` ruleset (read 2026-11-15) had `require_code_owner_review: false` and no required approvals; the release preflight checked only the tag ruleset. The history of `.github/release-signers` shows only the expected commits, so there is no sign the gap was used.
- **Severity.** Medium: a documented guarantee failed, and someone other than the user could exploit it.
- **Fix.** The owner turned on code-owner review on `main` on 2026-11-15, with approvals voided by a later push. In #13, `release-preflight` gained a `main-ruleset` check: it fails unless an active ruleset on `main` requires code-owner review and voids stale approvals, and unless its bypass list holds only the owner or the admin role.
- **Affected.** A repository setting, not code: no artifact to patch and nothing for users to do. No CVE: no released version holds the defect.

### F-06 (Medium): a release under a tag outside `v*` could take over the installer one-liner

- **Claim it broke.** The README and the install guide: the installer "checks the release's signature before it installs anything"; `docs/m4/packaging.md` §8: the script verifies what it installs. A script cannot verify itself: what `curl | sh` runs is trusted because of where it comes from, not because of the key written in it. The documented one-liner fetched `releases/latest/`, and the tag ruleset covered only `v*` tags.
- **Who, with what access.** The same as F-01: a writer to the repository, or a stolen token. F-01's fix did not close it.
- **Evidence.** The tag ruleset's scope and GitHub's release semantics, read live (2026-11-15). Not demonstrated, since that needs a GitHub write.
- **Severity.** Medium: a documented guarantee failed, a party other than the user could exploit it, and the impact would be code run as the user.
- **Fix.** The owner widened the tag ruleset to every tag (`~ALL`), with creation, update and deletion restricted to the owner, and turned on immutable releases (2026-11-15). In #13 the documented one-liner names the release (`…/releases/download/vX.Y.Z/fil-install.sh | sh -s -- --version X.Y.Z`), so it never reads `latest`; `just set-version` rewrites it; a tag's `release-check` fails unless `README.md` and `docs/user/install.md` give exactly that form at the release's version; both files have a code owner; and the preflight fails, rather than warns, when the tag ruleset does not cover every tag or immutable releases are off. The installer's header and `packaging.md` §8 now state the real trust root.
- **Affected.** No released version: the installer first ships in 1.0.0. No CVE.

### BUGS-1 (Medium, bug): `fil -N` asked the install question

- **Claim it broke.** DESIGN §7.3 and `docs/user/forwards.md`: `fil -N` asks nothing and runs in the background.
- **What happened.** The first `fil -N HOST` against a host without this version of fil asked whether to install it and read the terminal; as a background job it was stopped by `SIGTTIN` and held nothing.
- **Fix (#12).** A tunnel never asks: with `install = "ask"` it declines and names `fil install HOST`; with `install = "always"` it installs when started from a terminal. A binary test under a pty, with a fake `ssh` and an empty remote home, checks the foreground and a background process group: no question, no stop.
- **Affected.** No released version (`-N` is new in 1.0.0). Not a security issue.

### F-02 (Low): the macOS binary could be replaced between its build and its attestation

- **Claim it broke.** `docs/m4/release.md` §9 said the unowned self-test cannot reach an owned step and that the workflow refuses a duplicate artifact.
- **Who, with what access.** Someone who can already merge unowned code to `main`. That same access already reaches every binary through ordinary compilation (`crates/` has no code owner by design), so what this adds is concealment, for macOS only: the Linux binaries are rebuilt and compared by `release-verify`, the macOS binary is not.
- **Severity.** Low: defense in depth, plus a document that overstated. The lane rated it Medium; the verifier and the triage reviewer rated it Low. One of the two paths was reasoned, not reproduced.
- **Fix (#13).** Job outputs, which only the job that sets them can write, tie the release jobs together: `build-macos` records each universal binary's SHA-256, and `package` checks it before packaging and again in the archives; the man pages are built in a `docs` job of their own and handed over as one tar checked by its digest, whose members must be regular files or directories with no absolute or `..` path; `package` records the digest of `SHA256SUMS` before it runs anything from the archives; and `publish` checks that digest, and that it holds exactly `SHA256SUMS` and the files it lists, before it attests. `lint-workflow.sh` rule 12 keeps it all in place. The §9 sentences were corrected.
- **Residual (accepted).** The macOS binary is still not reproduced by any rebuild: its trust is this chain of CI jobs and the owner's signature. `--mac-rebuild` compares one by hand. No release is known to be affected.

### B-01 (Low): the QUIC port answers like a QUIC server

The privacy page, DESIGN §11 and the transports page said everything but the registered key is "dropped without an answer". In direct mode the port answers like any QUIC server: a Retry, and, to a peer offering fil's protocol, the daemon's per-run certificate, which names no host or user. Nothing is reachable without the registered key. The documents now say so (#11). The identification itself is accepted: TLS 1.3 sends the server's certificate before it judges the client's, the ALPN is frozen for 1.x (`docs/v1/wire.md` decision 7), and dropping Retry would invite amplification. Direct mode only.

### G-01 (Low): one UDP port per running daemon, not per user

With direct mode on, each running daemon has its own port, and since 1.0 each fil version runs its own daemon until its sessions end. DESIGN §8.3 and §11 and the privacy page now say one authenticated UDP port per running daemon (one per fil version), normally one (#11).

### G-02 (Low): which offline-input log is tidied

The log at the default path is tidied at every attach; a log at a path of the user's choosing is aged only while it is configured. The documents now say so (#11). Accepted for now: the file is the user's own and mode 0600. Tidying the last configured path too is scheduled.

### G-03 (Low): a sticky directory is accepted for the offline-input log

A world-writable directory with the sticky bit (such as `/tmp`) is accepted; a world-writable one without it is refused. Others cannot read or replace the 0600 file (it is opened without following links, and its owner, link count and mode are checked), but they can see its size and modification time. The documents and a comment at the check now say this (#11), and the behavior is accepted.

### G-04 (Low): `fil --version` named the home directory

The second line of `fil --version` printed the absolute path of a copy installed by hand, which names the user when a `--version` is pasted into a report. It now shows the home directory as `~` (#12), with a unit test. Not in a released version.

### E-01 (Low): short pastes are predicted without bracketed paste

The README and the guide said pasted text is never predicted. A paste is not predicted when the terminal marks it (bracketed paste) or when it arrives as 64 bytes or more; a shorter unmarked paste counts as typing. The documents and residual case 1 of the predictive-echo residuals now say so (#11). Accepted: it lies within that residual's conditions, and `predict = "off"` remains the way out. Treating a multi-key read as a boundary is to be considered after 1.0.

### F-03 (Low): no freshness on the indexes

fil's apt and dnf indexes carry no expiry, so a mirror or the site could serve an older signed release. The install guide and the installer's header now state the limit (#13). The installer half is closed by F-06's versioned one-liner, which never reads `latest`. Accepted for the repositories: an expiry would need the owner to re-sign on a schedule.

### BUGS-2 (Low, bug): a tunnel resizes a named session it takes over

`fil -N` attaching to a named session sets it to 80x24, since a tunnel has no terminal. `docs/user/forwards.md` says so (#11). The fix needs an added `Attach` field behind a feature bit, a 1.x addition; it is scheduled.

### BUGS-3 (Low, bug): tunnel status lines and a shared stderr

When a tunnel's stderr is not a terminal and is shared with other processes, writing its status lines changes the file status flags they share. The verifier found the lane's main scenario wrong (ssh does not inherit fil's stderr), so the effect is narrower than reported, borderline Info. A writer thread with a blocking write is scheduled.

### Info

- **G-05.** The daemon's panic hook logged the panic message at error level, and a panic message can quote the text being handled. It now logs the location at error level and the message only at debug (#12).
- **E-02.** `offline_input.confirm` (off by default) previews up to 36 characters typed while offline, masked at a known password prompt. The privacy page now lists it among what can draw a typed key (#11).
- **G-06.** The daemon logged its socket path, which holds the user id and version, at info. It is at debug now (#12).
- **F-04.** `taiki-e/install-action` moved to v2.90.5, by SHA, in the check workflows (#9) and in `release.yml` and `audit.yml` (#13). Every other action pin matched its tag's commit.
- **F-05.** `.github/package-signing-key-revoked.asc`, which the README cites, now has a code owner (#13).
- **A-01.** The relay's frozen hello reader is byte-exact: a non-canonical encoding of the hello's variant index, which the full decoder accepts, takes the documented fallback route. Only the user's own client writes there, and nothing after it is misparsed. `docs/v1/wire.md` decision 15 says so (#11), and `wire_golden` pins it (#12). Accepted by design.
- **A-02.** `docs/v1/wire.md` now says `Route` (index 18) is the last control message (#11).
- **C-01.** `fil install`'s answer reader does not count `FIL-*` and unknown marker lines toward its noise bound, as the attach path does. Every caller is already time-bounded, and a hostile host can stall as well by sending nothing. Scheduled.

## Not confirmed

None. The verifier confirmed every finding: five by reading alone (C-01, F-03, G-05, E-02 and G-06), the rest with probes, and two only in part:

- **F-02.** The path through the `package` job was confirmed by reading. A second path, through the self-test job replacing an artifact, is plausible from the artifact service's design but was not demonstrated, since that needs a workflow run on GitHub. #13's fix covers both.
- **BUGS-3.** The mechanism is real; the lane's scenario was not, and the verifier narrowed it.

The verifier also re-checked the redundancy and efficiency audit's ten "do before 1.0" items and found every claim true; they were done in #9 and #12 (the CI caching, the macOS release paths, nextest's kill timeout, a removed legacy opening path for never-released wire revisions, the shared duration parser, and smaller cleanups).

## Privacy review

- **Connections.** The client opens the pipe (ssh to the host the user named), a UDP connection to that host for direct mode (the address `ssh -G` gives, or `direct.address`), with the system resolver's lookup as ssh does, and the user's own agent socket. The daemon opens its Unix sockets, its UDP port when direct mode is on, loopback probes for `fil ports`, and the forwards the user asked for. Each is allowed by DESIGN §11.1 principle 1. `netwatch` sends nothing. The installer and the packages download only from the release URL the user ran. There is no telemetry, update check or crash reporting.
- **Logging.** At info and above: lifecycle, counts, modes and errors, with no host, session or path in the client, and, since G-06, none in the daemon. Debug adds session names, the host, policy settings and prediction counts. The default filter covers fil's crates only, so it carries no QUIC packet timing. Since G-05, a panic's message is logged at debug only.
- **What the host learns.** The client's version and wire, `TERM`, the window size, the laptop's short host name as the default takeover label (configurable), whether the agent is relayed, whether the client predicts, and the bytes typed. The jobs pre-check of `fil kill --outdated` returns counts only.
- **Other users on the host.** They can see that `/tmp/fil-$UID` exists, the `fil server --stdio` and bootstrap processes with their version, and the UDP port of each running daemon. They can reach `-R` ports on loopback unless `remote_peers = "same-user"` is set (documented).
- **On the laptop.** `client.log` (0600), and the offline-input log only when configured (G-02, G-03). Since G-04, `fil --version` does not name the home directory.
- Against `docs/user/security-privacy.md`, every statement holds as the page now reads (see the ledger).

## Dependencies and release integrity

- **Advisories.** `cargo deny` (advisories, bans, licenses, sources): all ok. The OSV API found nothing in the 254 locked packages (2026-11-15).
- **`deny.toml`.** All features; crates.io only; no ignored advisory; GPL-3.0-compatible licenses only.
- **Pins.** `rust-toolchain.toml` 1.99.1. The `Cross.toml` images, nfpm and the Debian and Fedora images by digest; pandoc by SHA-256; `just` and `cross` by version. Every action by full commit SHA; after F-04, each at its current release.
- **Workflows.** `release.yml` reads by default; only `publish` writes, mints an OIDC token or attests, and only on a `v*` tag; the crates.io job has an OIDC token only, in an environment the owner approves. No cache and no secret on the release path, `persist-credentials: false`, `--locked` builds. The check workflows are read-only; `audit.yml` runs on schedule and dispatch only. The lints pass.
- **Installer and repositories.** HTTPS-only fetches. The key written in the installer equals the `fil-release` line of `.github/release-signers` (`release-check`). The archive is checked against the signed `SHA256SUMS`, and nothing downloaded runs before verification except the installed `fil --version`. The apt and dnf indexes bind each file by SHA-256 and are signed with the package key; package and index signature checks are on. After F-06 the one-liner names its release; after F-03 the remaining replay limit of the repositories is documented.
- **Repository settings.** After F-01 and F-06: code-owner review required on `main` with stale approvals voided; a tag ruleset on every tag; immutable releases; bypass lists the owner's only. `release-preflight` checks all of them before every release.
- **CODEOWNERS.** It covers what decides what a release is or who signs it (`docs/m4/release.md` §9), now including the revoked package key (F-05), `README.md` and `docs/user/install.md`.
- **The last release.** Not verified by this audit: `release-verify` expects the layout that 1.0.0 introduces, and 0.3.0's own `verify.sh` was not run.
