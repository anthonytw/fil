# Packaging channels (M4 PKG)

> **Status: M4 package PKG** (`docs/m4/plan.md` §3 PKG, goal 3; the channels are the owner's, `docs/m4/release.md` §10.2). This page says how each v1 channel is built, checked and updated, and what is still the owner's. The user-facing install instructions are in the guide (`docs/user/install.md`); this page keeps the maintainer's side.

## 1. Installing

| Channel | Command | What you get |
|---|---|---|
| GitHub Releases | download, check, unpack (below) | the client, the remote bundle for `fil install`, man pages and completions |
| Homebrew (macOS, Linux) | `brew install anthonytw/tap/fil` | the same archive, unpacked into the Cellar |
| Debian, Ubuntu | `sudo apt install ./fil_<ver>_amd64.deb` (or `_arm64`) | the same files under `/usr`, from the release's Linux archive |
| Fedora, RHEL, openSUSE | `sudo rpm --import package-signing-key.asc`, then `sudo dnf install ./fil-<ver>-1.x86_64.rpm` (or `.aarch64`) | the same |
| Arch Linux | `fil-shell-bin` on the AUR (prepared, not published yet: §6) | the same |
| crates.io | `cargo install --locked fil-shell` | a build from source of the client and the remote for this machine only |
| Nix | `nix profile install github:anthonytw/fil/v<ver>` | a build from source, as with cargo |

- **Check what you download.** Every file of a release, the packages included, is in its `SHA256SUMS`, which the owner signs (`docs/m4/release.md` §4.2): `ssh-keygen -Y verify -f release-signers -I <principal> -n fil-release -s SHA256SUMS.sig < SHA256SUMS`, then `sha256sum -c --ignore-missing SHA256SUMS`. With gpg instead: `gpg --verify SHA256SUMS.asc SHA256SUMS` with the package key imported. The .rpm files are signed with the package key (`docs/m4/release.md` §10.4; its fingerprint is in the README and on the site), so rpm and dnf check them once the key is imported; the .deb files carry no signature of their own, because dpkg and apt check none, and are covered by `SHA256SUMS`.
- **By hand**, from a GitHub Release: unpack the archive for the machine and copy `bin/fil` into `~/.local/bin`. Copy it, don't symlink it: the install bootstrap refuses a symbolic link there (`docs/m4/install.md`). Keep `libexec/fil/remote/` beside it (`../libexec/fil/remote` from the binary) if you want `fil install` to upload the Linux binaries.
- **The names.** The command is `fil`, and so is the .deb and .rpm package (decided, owner 2026-11-04: D1). On crates.io the crate is `fil-shell`, and on the AUR the package is `fil-shell-bin`, because `fil` there belongs to unrelated projects (`docs/m4/release.md` §10.1): `cargo install fil` installs the wrong crate.
- **cargo and Nix build from source**, so they have no remote bundle, no man pages and no completions, and their binary is not a release build, so `fil install` will not upload it: name a release binary with `--binary`. The installed client works as a client, and as the remote on the same machine.

## 2. What a release carries

`release.yml` (`docs/m4/release.md` §9.1) now also builds, from the two reproducible Linux archives:

| File | From | Installs |
|---|---|---|
| `fil_<ver>_amd64.deb`, `fil-<ver>-1.x86_64.rpm` | `fil-<ver>-x86_64-linux-musl.tar.gz` | `/usr/bin/fil`, `/usr/libexec/fil/remote/…`, `/usr/share/…` |
| `fil_<ver>_arm64.deb`, `fil-<ver>-1.aarch64.rpm` | `fil-<ver>-aarch64-linux-musl.tar.gz` | the same |

- **The tool** is [nfpm](https://nfpm.goreleaser.com/) 2.48.0 (MIT; a build tool in no binary), run in its image pinned by the digest of its multi-architecture index (`NFPM_IMAGE` in `tests/release/common.sh`), with no network, and always as the image's linux/amd64 variant, like the archives' tar and gzip, so that CI and the VM's rebuild run the same nfpm binary. nfpm was chosen over cargo-deb and cargo-generate-rpm because it packages files that already exist: the packages hold the archive's own bytes, and no second cargo build is involved.
- **The layout** is the archive's under `/usr` (`package_path` in `tests/release/common.sh`), so the client finds its bundle at `../libexec/fil/remote` from `/usr/bin`, as from the archive's `bin/` (`docs/m4/release.md` §4.3). Docs go to `/usr/share/doc/fil/` (the rpm marks `LICENSE` as `%license`); the zsh completion goes to `vendor-completions/` in the .deb and `site-functions/` in the .rpm. Everything is owned by root, mode 0755 or 0644. There are no maintainer scripts and no dependencies (the binary is static), and the rpm owns no directory but its own; `release-check` enforces all three. The Maintainer (and the rpm's Packager) is `Anthony Wertz` with the address the owner gave for this field (D2), which appears only in `tests/release/linux-packages.sh`.
- **The version** is the package version with a pre-release's `-` as `~` (`0.1.0-rc.1` is `0.1.0~rc.1`, which sorts before `0.1.0`), and release 1. So a release version must be `X.Y.Z` or `X.Y.Z-PRE`, PRE of `[0-9A-Za-z.]` (nfpm's semver): `release-check` refuses another.
- **Signed** (D3): the owner signs the two rpms on their own machine after verifying the draft (`just release-sign-packages`, `docs/m4/release.md` §10.4), which also rewrites `SHA256SUMS` and writes `SHA256SUMS.asc`. CI builds them unsigned; no signing key is in CI.
- **Reproducible.** Every file and the package itself carry the time `SOURCE_DATE_EPOCH` (the tagged commit's, as for the archives), the rpm's build host is a fixed name, and the order is nfpm's own. The package job builds them twice (in the two assemblies of `package.sh`) and gates on identical bytes; `just release-verify` rebuilds them in the VM and compares hashes; for the signed rpms it compares everything after the signature header, which signing does not touch, and checks the signatures.
- **`SHA256SUMS`** lists the four archives and the four packages, sorted bytewise (`docs/m4/release.md` §4.2), and each package gets a build-provenance attestation like the archives.
- **`release-check`** reads each package without running anything from it (`tests/release/pkg_inspect.py`): the name `fil`, the version and architecture its file name says, exactly the files of its archive, byte for byte, at their places, root-owned, no maintainer script, no dependency, and, for an rpm, only its own directories and whether it is signed.
- **Install tests** (`tests/release/install-packages.sh`, `just packages-install DIR`): in Debian 13 and Fedora 45 containers pinned by digest, with no network, each package is installed, `fil --version` must print the release's first line, the bundle must check, `dpkg --verify` or `rpm -V` must pass, and removing it must leave no file behind. With `--key KEY.asc` (for signed rpms) the key is imported and the rpm is installed with its signature checked. `release.yml` runs the amd64 ones in the package job and the arm64 ones on an arm64 runner (`packages-arm64`); the draft is not made unless both pass.

## 3. crates.io

- **The nine crates:** `fil-shell` (the package in `crates/fil`, renamed from `fil`; its binary and library keep the name `fil`) and `fil-proto`, `fil-transport`, `fil-forward`, `fil-term`, `fil-predict`, `fil-client`, `fil-session`, `fil-daemon`. Each says `publish = ["crates-io"]` and has a `LICENSE`, a link to the root one, which cargo packages as the file's text (GPL-3.0 §4: every published copy of the source carries the license); `fil-testkit`, `fil-testbins` and `fil-netsim` say `publish = false`.
- **Dependencies between them** come from `[workspace.dependencies]` in the root `Cargo.toml`: a path, and an exact version (`=X.Y.Z`), so `fil-shell X.Y.Z` builds against the X.Y.Z of each library and nothing else. A release bump changes the version there with `[workspace.package] version`: `just set-version X.Y.Z` (cargo refuses a requirement the path crate does not meet, and `just release-test` checks they agree). Dev-dependencies stay bare paths, which `cargo publish` drops, so the test-only crates are never needed on crates.io. For the same reason fil-predict's PTY harness moved from `src/pty.rs` into its examples (`examples/support/pty.rs`): as a library module it made the unpublished fil-netsim a dependency.
- **`just crates-check`** (`tests/release/publish-crates.sh --dry-run`, also a step of release.yml's `prepare`): `cargo publish --workspace --dry-run --locked`, which packages and verifies each crate in dependency order against a local overlay of the others; the packaged `fil-shell` is built, and every crate's package must list `LICENSE`. It was run at the workspace's version and at 0.1.0 when PKG was built.
- **Publishing** (N8): release.yml's `crates-io` job, on the tag push only, in the `crates-io` environment that only the owner approves, with `id-token: write` and nothing else. It checks the tag as `prepare` does (v<version>, annotated, on main, signed by the release key, and still naming the commit this run checked out, so a deployment approved after the tag was moved publishes nothing), then `tests/release/crates-io-gate.sh` (with `actions: read`, which reading the environment needs; `prepare` runs the environment half on every run): the environment's required reviewers include the owner, the release is published, and its `SHA256SUMS.sig` verifies against `.github/release-signers` on main. Then it exchanges the job's OIDC identity for a short-lived token with `rust-lang/crates-io-auth-action` (pinned by commit), and publishes the crates one at a time in dependency order (computed from `cargo metadata`), skipping a version already there, so a re-run resumes. **It compiles nothing:** `cargo publish --no-verify`, so no build script or proc macro of any crate runs beside the token; `prepare` verified the same commit with `just crates-check`. The owner creates and protects the environment before adding the trusted publishers (`docs/m4/release.md` §10.1). The owner approves the deployment **after** step 4 of `docs/m4/release.md` §9.2; the run waits for the approval (up to 30 days).
- **The notices** (`docs/m4/release.md` §7): cargo-about used to skip the workspace's crates because they were all `publish = false`. It cannot skip the published ones by config (its `private.registries` would also skip any registry crate whose manifest says `publish = ["crates-io"]`, as serial2's does), so `about.hbs` leaves out every crate and license entry with no registry source, and `tests/release/notice_workspace.py` fails `just notices` if a license entry ever mixes the workspace's crates with registry crates. The rendered file is unchanged apart from the package's name.

## 4. Homebrew

- **The formula** is generated, never written by hand: `packaging/homebrew/fil.rb.in` is the template, and `just brew-formula VERSION` (`packaging/render.sh brew`) fills in the version and the three archives' checksums from the release's `SHA256SUMS`, by default the copy that `just release-verify VERSION` verified and the owner signed (`target/release-verify/VERSION/files/SHA256SUMS`). It downloads the universal macOS archive on macOS and the matching Linux archive on Linux, installs `bin/fil`, `libexec/fil/remote/` (so `fil install` finds its bundle in the Cellar), the man pages, the completions and the docs, and its `test do` block runs `fil --version` and checks the bundle against its `SHA256SUMS`.
- **The plan's attach test is left out of `test do`** (`docs/m4/plan.md` PKG asked for a local pipe attach in a temporary `HOME`): the daemon's socket directory is `/tmp/fil-$UID`, not under `HOME`, so a test attach would start, or reuse, a daemon of the user's own and leave it running after the test. The release's smoke and drop-in tests cover the attach.
- **How the tap gets each release, with no token in fil's CI** (proposed):
  1. after the owner publishes the release (§9.2), the coordinator runs `just brew-formula X.Y.Z` on the verified `SHA256SUMS`;
  2. it opens a PR in `anthonytw/homebrew-tap` that adds or replaces `Formula/fil.rb`, with `gh` as `splarg-bot` (which has Write on the tap); fil's workflows hold no credential for the tap;
  3. the tap's own CI (`brew test-bot`, or at least `brew audit --strict` and `brew install` and `brew test` on macOS and Linux), once the tap has one, tests the PR; the owner merges it, or the bot does if the owner allows it (`docs/m4/plan.md` §5, SHIP step 4).

  The tap's first PR (the formula, its CI and a README) is a task in that repository, not in fil.
- **Tested** (2026-11-06): the formula renders against a release dry run's archives (run 41899619926, version 0.0.0, `file://` URL base) and parses. It was run through `brew install`, `brew test` and `brew audit --strict` on the runners by the `brew` suite (below; local Homebrew is not writable by the agent seat). The tap has CI (`brew style`, then audit, install and test of each changed formula).
- **The `brew` suite of `macos-check.yml`** (`gh workflow run macos-check -f ref=BRANCH -f suite=brew -f release_run=RUN_ID`; in `all` it runs when `release_run` is given) takes a `release` dry run by ID instead of building: the job downloads that run's `release-files` artifact with its own token (`actions: read`, nothing else), which costs about a minute where building the universal binary and the Linux archives takes the release workflow about 20 minutes, and it is the formula that is under test. It renders the formula against the files with a `file://` URL base (which Homebrew accepts), puts it in a scratch tap (`brew tap-new fil-check/tap`; Homebrew no longer installs a formula from a bare file), then runs `brew install --formula`, `brew test` and `brew audit --strict` on Apple silicon (`macos-15`) and Intel (`macos-15-intel`), and removes the tap. `--online` is not run: it checks the URL, the homepage and the version against the network, and the dry run's version has no release at that URL.
- **First run found three audit failures,** fixed in the template: a `version` line redundant with the one scanned from the URL, `url` and `sha256` inside `on_macos` (Homebrew allows only a few directives there: the universal macOS archive is now the formula's own `url`, and `on_linux` overrides it), and two lines over 118 columns. Then `url` before `license`, and empty man-page and doc lists skipped (Homebrew warns; the dry run's archive has no man pages yet). Green on both architectures: run 42249513101 against dry run 41899619926. A release version whose archive name Homebrew cannot scan (a pre-release such as `0.1.0-rc.1`) would need `version` back; `brew audit` says so.

## 5. Nix

- **`flake.nix`** at the root builds `fil-shell` from source with the toolchain `rust-toolchain.toml` pins (from rust-overlay; nixpkgs' rustc can be older than the workspace's `rust-version`), for x86_64 and aarch64 Linux and macOS. `nix build`, `nix run . -- --version`, `nix profile install github:anthonytw/fil/vX.Y.Z`. It skips the test suite (`doCheck = false`: the tests need PTYs, sockets and real time, and `just ci` runs them). `flake.lock` pins nixpkgs and rust-overlay; `nix flake update` moves them.
- **Checked** when PKG was built, in a `nixos/nix` container (Nix 2.35) in the lab VM on aarch64-linux: `nix flake lock`, `nix build .#fil` and `nix run .#fil -- --version`, which printed `fil 0.0.0 (wire 1.13)`. Not checked: x86_64-linux and the two macOS systems (no Nix on the Mac).
- **nixpkgs:** `docs/m4/nixpkgs-pr.md` is the draft of the package and the PR, for after the release.
