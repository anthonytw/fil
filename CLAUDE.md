# fil: guidance for Claude

fil is a remote shell for development over SSH:

- reconnect with native scrollback
- sessions you can reattach or take over from another machine
- port forwards that survive reconnects
- optional predictive echo
- two transports: a pipe (ssh) and direct QUIC

## Start here

- **`DESIGN.md` is the source of truth.**
  - Items marked **(decided)** are the owner's decisions. Build on them; don't reopen them.
  - Everything else is a proposal and can change. When one changes, update `DESIGN.md` in the same PR.
- **Open questions** are in `DESIGN.md` §16. **Milestones** are in §15. Work goes riskiest first. M0, M1 and M2 are done (`docs/m2/plan.md` is M2's historical work order); M3 shipped in 0.2.0, with its follow-ups in 0.3.0, and M4 is built with its sweep in progress (`docs/m3/plan.md`, `docs/m4/plan.md`).
- **Ask before starting unrequested work.** Propose it and wait for the owner's OK. A question like "how hard would X be?" wants a feasibility answer, not an implementation.

## Conventions

- **Rust:** a cargo workspace, laid out as in `DESIGN.md` §13. Crates live in `crates/`. The toolchain is pinned in `rust-toolchain.toml`.
- **Tests:** keep them proportionate. Unit-test the logic that is easy to get wrong, such as frame parsing, sequence numbers and the snapshot writer. Heavy harnesses, like the fidelity suite and randomized overlay runs, are commands you run on demand, not part of `just ci` (GitHub's `suite=check` runs a few of them on every PR, below). Tests run in two tiers (`docs/dev/timing-tests.md` "Tiers"): the per-PR gate and `just ci-release`, before a release. A test with a size (seeds, connections, MiB) picks it with `fil_testkit::scale::pick(VAR, smoke, full)`: `FIL_TEST_SCALE=smoke` (the default) per PR, `full` in the release suite, and its own variable overrides both; a test with no small form is named `soak_*` and runs only in the release suite. `.config/nextest.toml` (cargo-nextest) classes each test binary as logic (Linux only) or OS (Linux and macOS): add a new OS binary to its `os` profile. A test whose pass or fail depends on real elapsed time is named `wallclock_*` and runs alone in `just test-wallclock`, which is not in `just ci` (shared CI runners stall) but in `just ci-release`, run on a quiet Mac before a release; run it locally too when a change touches what such a test measures (pacing, forwards, latency) (`docs/dev/timing-tests.md`: P and T bounds, `fil_testkit::timing::Stalls`); a bound that is a DESIGN.md claim is never relaxed to make CI pass.
- **Logging:** `tracing`, with JSON output.
- **POSIX calls:** library and binary code uses `rustix`. `nix` is for tests and examples only. The one exception is `fil-session`, which keeps `nix` because portable-pty's API hands over nix types (the PTY master's termios) and its signal and uid calls were not converted separately; new code there uses rustix where it can.
- **License:** GPL-3.0-or-later. Every dependency must be GPL-3.0-compatible:
  - fine: MIT, Apache-2.0, BSD, ISC, MPL-2.0, LGPL, GPL-3.0
  - not allowed: GPL-2.0-only, or anything proprietary
- **Diagrams in Markdown are Mermaid, never ASCII art.**
  - Render-check every new or changed diagram before committing, for example with `npx @mermaid-js/mermaid-cli`.
  - Terminal-output mockups (like `fil ports` in `DESIGN.md`) stay as plain code blocks.
- **The wire has a revision.** `PROTOCOL_REVISION` in `crates/fil-proto/src/limits.rs` **must change whenever any message encoding changes**: a field or variant of a control message, the data segment, the QUIC stream layout, a limit a decoder enforces. Builds of different revisions refuse each other at the hello, and the revision is in the daemon's socket name so their daemons coexist (`DESIGN.md` §5.3, §8.5). `crates/fil-proto/tests/golden/wire.txt` is a committed encoding of every message, tagged with the revision; `just ci` fails if the encoding changes without a bump. To change the wire: bump `PROTOCOL_REVISION`, run `just wire-golden`, commit the golden with the change. The golden also covers every decoder limit and the widest value of each field, and its `[history]` makes two PRs that bump to the same revision conflict in git: when it does, take main's, bump past it and regenerate. `target/*/fil` after a `cargo test` or an example build has the test hooks (`FIL_TEST_*`) in it and is not a release binary; the recipes that install it (`pi-e2e`, `dropin`) build it in an invocation of its own and `just no-test-hooks` checks. The preamble, the hello, the opening ping and pong (`fil_proto::opening`: fixed bytes the relay routes by, not control messages) and the frame layout are *frozen* within a `PROTOCOL_MAJOR`: a `[frozen]` line in the golden may be added (with a revision) and never changed, so a relay of any revision from 3 on can route a client of any other. An added line may only pin something no older peer has to read (a new probe, a new fact); a new form of the opening or the hello that a peer sends or must accept needs a new `PROTOCOL_MAJOR`.
- **The security invariants in `DESIGN.md` §11 are requirements:** the fixed remote commands: `fil server --stdio` and the constant bootstrap (decided, owner 2026-11-04; DESIGN §8.2); no secrets at rest; peer-UID checks; pinned certificates. A change that weakens any of them needs the owner's sign-off.

## Delivery

- **Home:** GitHub (`anthonytw/fil`, the `origin` remote) since 2026-11-14: PRs, CI and merges happen there, and its `main` ruleset requires the gate's checks (below). The private Gitea (`gitea` remote) is a backup: a launchd job on the coordinator's Mac fast-forwards Gitea's `main` to GitHub's every ten minutes (`main` only, never forced; no tags, because Gitea's `v0.1.0` and `v0.2.0` are marker tags that differ from GitHub's). Don't push to Gitea by hand. From 2026-11-06 to 2026-11-13 Gitea was the home and GitHub a mirror; PRs #1 to #100 of that time are on Gitea.
- **Workflow:** branch, then PR, then squash merge, through `gh` (`gh pr create --base main ...`, then `gh pr merge --squash`). One task per PR. Keep GitHub activity low: few pushes per PR (each push runs the gate, and a newer push cancels the older run), polling at 60 s or slower, no loops of reruns, and never create a GitHub account. Never push tags (the owner tags at release time) or push `main` directly.
- **The merge gate** (since 2026-11-09) is three things, on the branch rebased on (or merged with) current `main`:
  1. **Local, on the Mac:** the tests for what the change touches (`cargo test -p CRATE FILTER`, the affected harness or `just release-test` for release tooling) plus `just fmt-check clippy deny`. The full `just ci` is not required locally; run it when a change is broad (it needs cargo-nextest). Say in the PR what ran.
  2. **GitHub:** a green `linux-check` and `macos-check` (`suite=check`) on the PR head, which a pull request runs by itself (a branch pushed without a PR can still be checked by dispatch: `gh workflow run linux-check.yml --ref BRANCH -f ref=SHA -f suite=check`, the same for `macos-check.yml`); about 10 minutes of wall time (about 21 when the change touches the release paths: macOS's `release-test (arm64)` runs the whole selftest). `linux-check` runs `lint` (`just lint`: `cargo deny` with the fetched RustSec database, `just notices`, `ci-workflow-test`, `exporter-lock`, fmt, clippy, the default-features check, `just release-deps`; then the drop-in quick set against a private daemon, `just dropin --local --set quick`), `check` (`just test`: every test, logic and OS, at smoke size, without the `wallclock_` and `soak_` tests; and the per-PR harnesses) on x86_64 Linux, and `release-test` (the release scripts' own tests) when the change touches the release paths (`tests/ci/release-paths.sh`). `macos-check` runs on Apple silicon only: `check (arm64)` (clippy, `just test-os`, the OS tests, since pure logic runs on Linux; a cross `cargo check` of the Intel build; the PTY tests) and `release-test (arm64)` on the release paths (not in `suite=all`, where linux-check's release-test runs once). No Intel test run is left (brew's Intel job and release.yml's Rosetta run of the universal binary remain). These job names are what a ruleset requires; `release.sh` also tells a `suite=all` run by its jobs (`full-scale (1/3)` with `check`, `aarch64` and `terminals` on Linux; `dropin (arm64)` with `check (` and `remote (` on macOS), so keep those names too. The workflow files list the steps; `docs/dev/timing-tests.md` "Tiers" maps everything to its tier. Not per-PR any more: the static musl builds and the aarch64 Linux tests (the Orin jobs); `suite=realnet`, `suite=aarch64` and the release build cover the builds, and `just vm-run just ci` (the Mac's aarch64 Linux VM) or `just pi-e2e` the aarch64 tests; use them when a change touches the build or platform code. Delete the branch after the merge.
  3. **An independent review**, privacy included.
  `suite=extended` (about 15 min) runs once per merge batch on `main` (below), and per PR when a change is in its area: the gate, the macOS prediction harness and drop-in quick set, realnet's functional parts, the terminals, the arm64 smoke run and macOS as the remote host (user sshd). The release candidate, `suite=all` (about 20 min, `tests/release/just.sh release` dispatches it), and `just ci-release` (on a quiet Mac, about 20 min: only what needs a quiet host and a real clock: the wall-clock tests, pacing, fidelity with its performance checks, the prediction harness at its defaults and the prediction matrix; `just ci-release-full` is the old whole list, for a release without GitHub) run before a release; the area suites (`suite=realnet`, `aarch64`, `arm64-remote`, `terminals`, `latency`, `remote`, `brew`) when a change is in their area. None is per-PR.
- **Gitea CI** (`.gitea/workflows/ci.yml`, the self-hosted aarch64 runner) is manual only since 2026-11-09 (`workflow_dispatch`): it is no longer a merge gate. Its push-to-main skip (`tests/ci/push_skip.py`, issue #38) stays for the day it runs on pushes again.
- **GitHub's `main` moves only by merged PRs; tags are the owner's.** The ruleset blocks deletion, non-fast-forward pushes and merges without the gate; tags are pushed by the owner, at release time only. Each push of `main` runs `linux-check` and `macos-check` with `suite=extended` by itself (the `push` trigger, `branches: [main]` only): those runs check the merge batch and are the only ones that save the rust-cache (`save-if`), which every PR run then restores. Every pull request on GitHub runs the gate (`pull_request`, never `pull_request_target`; a fork's run has a read-only token and no secret); `tests/release/lint-workflow.sh --check` (C2) allows exactly these triggers beside `workflow_dispatch`. A fork's PR runs only after the owner approves it (the repository's Actions setting for outside contributors). The workflows under `.github/workflows/` run there only (Gitea ignores them, because `.gitea/workflows/` exists); `release.yml` (and any new workflow) is listed in CODEOWNERS, so the owner merges changes to it; the two check workflows are not. CODEOWNERS covers only what decides what a release is or who signs it (`docs/m4/release.md` §9); the release path's recipes are in `tests/release/release.just`, run as `tests/release/just.sh RECIPE` (the owner's release commands too: `tests/release/just.sh release X.Y.Z`), never through the unowned `justfile`, and `tests/release/recipes.sh` keeps it that way. On GitHub:
  - **Linux check:** `linux-check` runs the gate's `lint`, `check` and `release-test` (above); `suite=extended` adds realnet's functional parts, the terminals, aarch64 and the arm64 smoke run; `suite=all` adds `full-scale` (`just test-release K/3`: every test at full size, the soaks included, in three shards), release-test always, every realnet part and the full arm64 run. `suite=realnet` runs the real-network harness (real OpenSSH in Docker, NAT and `tc netem` in network namespaces, on static x86_64 musl binaries; `just realnet` on a Linux box, see `docs/m1/realnet.md`); `suite=aarch64` builds the static aarch64 binary (`docs/m1/pi.md`); `suite=arm64-remote` builds it and runs it as the remote host on GitHub's arm64 Linux runner, behind the Pis' gate verbs in a network namespace (`tests/arm64/`), with `pi_e2e` and the full drop-in suite with prediction on (in two shards, without the four forward scenarios realnet runs on the real network: the cable pull, reconnect, swap and sleep): the run the test Pis used to be, which replaced them as a release gate (owner, 2026-11-11; the Pis are optional, `just pi-e2e`); `suite=terminals` replays fil's terminal writes (snapshots, the prediction overlay, status lines, resizes) into real xterm, kitty, WezTerm and tmux under Xvfb and reads the screens back (`tests/terminals/run.sh`, `docs/m3/terminals.md`; rerun it whenever `overlay.rs` or the snapshot writer changes a byte it writes); realnet's forward part runs in CI as `fwd-func`, `fwd-cable` (the only cable pull), `fwd-stress`, `fwd-perf-a` and `fwd-perf-b`. Agents dispatch `suite=check` per PR (the gate) and the other suites only when a change is in their area.
  - **macOS check:** `macos-check` (`suite=check|extended|all|remote|brew`; `brew` tests the Homebrew formula on Apple silicon and Intel and needs a release run) is the same kind of check on GitHub's macOS runners, Apple silicon only: per PR (`suite=check`) the OS tests and the PTY tests (above); `suite=extended` adds the prediction harness, the drop-in quick set and the remote host over the user-mode sshd; `suite=all` the full drop-in suite in a job of its own (`dropin (arm64)`) and both sshds; macOS as the remote host is a real ssh login (`just macos-remote`, `tests/macos/`).
  - **Release:** `release.yml` builds the release and its dry run (`docs/m4/release.md`).
- **Signing:** the global git config SSH-signs commits. Don't disable it.
- **The repo is public.** Everything pushed to GitHub, a PR branch included, is world-visible, including history, which GitHub keeps, so never commit secrets, IP addresses or personal data, not even in a work-in-progress commit.
- **Reviews and sweeps.**
  - Every PR gets an independent review, and the review always covers **user privacy** (DESIGN.md §11.1) alongside correctness and security.
  - Every milestone ends with a whole-tree **sweep** (DESIGN.md §15): independent audits for redundancy, efficiency, user privacy, security and bugs, then fix PRs, then a verification pass.
  - Privacy here means what fil reveals about the people using it, not just keeping our own secrets out of the repo.
