# Packaging channels (M4 PKG)

> **Status: M4 package PKG** (`docs/m4/plan.md` §3 PKG, goal 3; the channels are the owner's, `docs/m4/release.md` §10.2). This page says how each v1 channel is built, checked and updated, and what is still the owner's. The user-facing install instructions are in the guide (`docs/user/install.md`); this page keeps the maintainer's side.

## 1. Installing

| Channel | Command | What you get |
|---|---|---|
| The installer (from the release after 0.3.0) | `curl -fsSL https://github.com/anthonytw/fil/releases/latest/download/fil-install.sh \| sh` (§8) | the client in `~/.local/bin` and the remote bundle beside it, after checking the signature and the checksum |
| GitHub Releases | download, check, unpack (below) | the client, the remote bundle for `fil install`, man pages and completions |
| Homebrew (macOS, Linux) | `brew install anthonytw/tap/fil` | the same archive, unpacked into the Cellar |
| Debian, Ubuntu | `sudo apt install ./fil_<ver>_amd64.deb` (or `_arm64`) | the same files under `/usr`, from the release's Linux archive |
| Fedora, RHEL, openSUSE | `sudo rpm --import package-signing-key.asc`, then `sudo dnf install ./fil-<ver>-1.x86_64.rpm` (or `.aarch64`) | the same |
| fil's apt and dnf repositories (from the release after 0.3.0) | `apt install fil`, `dnf install fil` after the one-time setup in `docs/user/install.md` (§7) | the same packages, upgraded with the system |
| Arch Linux | `fil-shell-bin` on the AUR (prepared, not published yet: §6) | the same |
| crates.io | `cargo install --locked fil-shell` | a build from source of the client and the remote for this machine only |
| Nix | `nix profile install github:anthonytw/fil/v<ver>` | a build from source, as with cargo |

- **Check what you download.** Every file of a release, the packages included, is in its `SHA256SUMS`, which the owner signs (`docs/m4/release.md` §4.2): `ssh-keygen -Y verify -f release-signers -I <principal> -n fil-release -s SHA256SUMS.sig < SHA256SUMS`, then `sha256sum -c --ignore-missing SHA256SUMS`. With gpg instead: `gpg --verify SHA256SUMS.asc SHA256SUMS` with the package key imported. The .rpm files are signed with the package key (`docs/m4/release.md` §10.4; its fingerprint is in the README and on the site), so rpm and dnf check them once the key is imported; the .deb files carry no signature of their own, because dpkg and apt check none, and are covered by `SHA256SUMS`.
- **By hand**, from a GitHub Release: unpack the archive for the machine and copy `bin/fil` into `~/.local/bin`. Copy it, don't symlink it: the install bootstrap refuses a symbolic link there (`docs/m4/install.md`). Keep `libexec/fil/remote/` beside it (`../libexec/fil/remote` from the binary) if you want `fil install` to upload the Linux binaries.
- **The names.** The command is `fil`, and so is the .deb and .rpm package (decided, owner 2026-11-04: D1). On crates.io the crate is `fil-shell`, and on the AUR the package is `fil-shell-bin`, because `fil` there belongs to unrelated projects (`docs/m4/release.md` §10.1): `cargo install fil` installs the wrong crate.
- **cargo and Nix build from source**, so they have no remote bundle, no man pages and no completions, and their binary is not a release build, so `fil install` will not upload it: name a release binary with `--binary`. The installed client works as a client, and as the remote on the same machine.

## 2. What a release carries

`release.yml` (`docs/m4/release.md` §9.1) now also builds, from the two reproducible Linux archives:

| File | From | Installs |
|---|---|---|
| `fil_<ver>_amd64.deb`, `fil-<ver>-1.x86_64.rpm` | `fil-<ver>-x86_64-linux-musl.tar.gz` | `/usr/bin/fil`, `/usr/libexec/fil/remote/…`, `/usr/share/…` |
| `fil_<ver>_arm64.deb`, `fil-<ver>-1.aarch64.rpm` | `fil-<ver>-aarch64-linux-musl.tar.gz` | the same |

- **The tool** is [nfpm](https://nfpm.goreleaser.com/) 2.48.0 (MIT; a build tool in no binary), run in its image pinned by the digest of its multi-architecture index (`NFPM_IMAGE` in `tests/release/common.sh`), with no network, and always as the image's linux/amd64 variant, like the archives' tar and gzip, so that CI and the VM's rebuild run the same nfpm binary. nfpm was chosen over cargo-deb and cargo-generate-rpm because it packages files that already exist: the packages hold the archive's own bytes, and no second cargo build is involved.
- **The layout** is the archive's under `/usr` (`package_path` in `tests/release/common.sh`), so the client finds its bundle at `../libexec/fil/remote` from `/usr/bin`, as from the archive's `bin/` (`docs/m4/release.md` §4.3). Docs go to `/usr/share/doc/fil/` (the rpm marks `LICENSE` as `%license`); the zsh completion goes to `vendor-completions/` in the .deb and `site-functions/` in the .rpm. Everything is owned by root, mode 0755 or 0644. There are no maintainer scripts and no dependencies (the binary is static), and the rpm owns no directory but its own; `release-check` enforces all three. The Maintainer (and the rpm's Packager) is `Anthony Wertz` with the address the owner gave for this field (D2), which appears only in `tests/release/linux-packages.sh`.
- **The version** is the package version with a pre-release's `-` as `~` (`0.1.0-rc.1` is `0.1.0~rc.1`, which sorts before `0.1.0`), and release 1. So a release version must be `X.Y.Z` or `X.Y.Z-PRE`, PRE of `[0-9A-Za-z.]` (nfpm's semver): `release-check` refuses another.
- **Signed** (D3): the owner signs the two rpms on their own machine after verifying the draft (`tests/release/just.sh release-sign-packages`, `docs/m4/release.md` §10.4), which also rewrites `SHA256SUMS` and writes `SHA256SUMS.asc`. CI builds them unsigned; no signing key is in CI.
- **Reproducible.** Every file and the package itself carry the time `SOURCE_DATE_EPOCH` (the tagged commit's, as for the archives), the rpm's build host is a fixed name, and the order is nfpm's own. The package job builds them twice (in the two assemblies of `package.sh`) and gates on identical bytes; `tests/release/just.sh release-verify` rebuilds them in the VM and compares hashes; for the signed rpms it compares everything after the signature header, which signing does not touch, and checks the signatures.
- **`SHA256SUMS`** lists the five archives (the macOS one twice), the four packages and the installer (§8), sorted bytewise (`docs/m4/release.md` §4.2), and each package gets a build-provenance attestation like the archives.
- **`release-check`** reads each package without running anything from it (`tests/release/pkg_inspect.py`): the name `fil`, the version and architecture its file name says, exactly the files of its archive, byte for byte, at their places, root-owned, no maintainer script, no dependency, and, for an rpm, only its own directories and whether it is signed.
- **Install tests** (`tests/release/install-packages.sh`, `just packages-install DIR`): in Debian 13 and Fedora 45 containers pinned by digest, with no network, each package is installed, `fil --version` must print the release's first line, the bundle must check, `dpkg --verify` or `rpm -V` must pass, and removing it must leave no file behind. With `--key KEY.asc` (for signed rpms) the key is imported and the rpm is installed with its signature checked. `release.yml` runs the amd64 ones in the package job and the arm64 ones on an arm64 runner (`packages-arm64`); the draft is not made unless both pass.

## 3. crates.io

- **The nine crates:** `fil-shell` (the package in `crates/fil`, renamed from `fil`; its binary and library keep the name `fil`) and `fil-proto`, `fil-transport`, `fil-forward`, `fil-term`, `fil-predict`, `fil-client`, `fil-session`, `fil-daemon`. Each says `publish = ["crates-io"]` and has a `LICENSE`, a link to the root one, which cargo packages as the file's text (GPL-3.0 §4: every published copy of the source carries the license); `fil-testkit`, `fil-testbins` and `fil-netsim` say `publish = false`.
- **Dependencies between them** come from `[workspace.dependencies]` in the root `Cargo.toml`: a path, and an exact version (`=X.Y.Z`), so `fil-shell X.Y.Z` builds against the X.Y.Z of each library and nothing else. A release bump changes the version there with `[workspace.package] version`: `just set-version X.Y.Z` (cargo refuses a requirement the path crate does not meet, and `just release-test` checks they agree). Dev-dependencies stay bare paths, which `cargo publish` drops, so the test-only crates are never needed on crates.io. For the same reason fil-predict's PTY harness moved from `src/pty.rs` into its examples (`examples/support/pty.rs`): as a library module it made the unpublished fil-netsim a dependency.
- **`just crates-check`** (`tests/release/publish-crates.sh --dry-run`, also a step of release.yml's `prepare`): `cargo publish --workspace --dry-run --locked`, which packages and verifies each crate in dependency order against a local overlay of the others; the packaged `fil-shell` is built, and every crate's package must list `LICENSE`. It was run at the workspace's version and at 0.1.0 when PKG was built.
- **Publishing** (N8): release.yml's `crates-io` job, on the tag push only, in the `crates-io` environment that only the owner approves, with `id-token: write` and nothing else. It checks the tag as `prepare` does (v<version>, annotated, on main, signed by the release key, and still naming the commit this run checked out, so a deployment approved after the tag was moved publishes nothing), then `tests/release/crates-io-gate.sh` (with `actions: read`, which reading the environment needs; `prepare` runs the environment half on every run): the environment's required reviewers include the owner, the release is published, and its `SHA256SUMS.sig` verifies against `.github/release-signers` on main. Then it exchanges the job's OIDC identity for a short-lived token with `rust-lang/crates-io-auth-action` (pinned by commit), and publishes the crates one at a time in dependency order (computed from `cargo metadata`), skipping a version already there, so a re-run resumes. **It compiles nothing:** `cargo publish --no-verify`, so no build script or proc macro of any crate runs beside the token; `prepare` verified the same commit with `just crates-check`. The owner creates and protects the environment before adding the trusted publishers (`docs/m4/release.md` §10.1). The owner approves the deployment **after** step 4 of `docs/m4/release.md` §9.2; the run waits for the approval (up to 30 days).
- **The notices** (`docs/m4/release.md` §7): cargo-about used to skip the workspace's crates because they were all `publish = false`. It cannot skip the published ones by config (its `private.registries` would also skip any registry crate whose manifest says `publish = ["crates-io"]`, as serial2's does), so `about.hbs` leaves out every crate and license entry with no registry source, and `tests/release/notice_workspace.py` fails `just notices` if a license entry ever mixes the workspace's crates with registry crates. The rendered file is unchanged apart from the package's name.

## 4. Homebrew

- **The formula** is generated, never written by hand: `packaging/homebrew/fil.rb.in` is the template, and `just brew-formula VERSION` (`packaging/render.sh brew`) fills in the version and the three archives' checksums from the release's `SHA256SUMS`, by default the copy that `tests/release/just.sh release-verify VERSION` verified and the owner signed (`target/release-verify/VERSION/files/SHA256SUMS`). It downloads the universal macOS archive on macOS and the matching Linux archive on Linux, installs `bin/fil`, `libexec/fil/remote/` (so `fil install` finds its bundle in the Cellar), the man pages, the completions and the docs, and its `test do` block runs `fil --version` and checks the bundle against its `SHA256SUMS`.
- **The plan's attach test is left out of `test do`** (`docs/m4/plan.md` PKG asked for a local pipe attach in a temporary `HOME`): the daemon's socket directory is `/tmp/fil-$UID`, not under `HOME`, so a test attach would start, or reuse, a daemon of the user's own and leave it running after the test. The release's smoke and drop-in tests cover the attach.
- **How the tap gets each release, with no token in fil's CI** (proposed):
  1. after the owner publishes the release (§9.2), the coordinator runs `just brew-formula X.Y.Z` on the verified `SHA256SUMS`;
  2. it opens a PR in `anthonytw/homebrew-tap` that adds or replaces `Formula/fil.rb`, with `gh` as an automation account (which has Write on the tap); fil's workflows hold no credential for the tap;
  3. the tap's own CI (`brew test-bot`, or at least `brew audit --strict` and `brew install` and `brew test` on macOS and Linux), once the tap has one, tests the PR; the owner merges it, or the bot does if the owner allows it (`docs/m4/plan.md` §5, SHIP step 4).

  The tap's first PR (the formula, its CI and a README) is a task in that repository, not in fil.
- **Tested** (2026-11-06): the formula renders against a release dry run's archives (run 41899619926, version 0.0.0, `file://` URL base) and parses. It was run through `brew install`, `brew test` and `brew audit --strict` on the runners by the `brew` suite (below; local Homebrew is not writable by the agent account). The tap has CI (`brew style`, then audit, install and test of each changed formula).
- **The `brew` suite of `macos-check.yml`** (`gh workflow run macos-check -f ref=BRANCH -f suite=brew -f release_run=RUN_ID`; in `all` it runs when `release_run` is given) takes a `release` dry run by ID instead of building: the job downloads that run's `release-files` artifact with its own token (`actions: read`, nothing else), which costs about a minute where building the universal binary and the Linux archives takes the release workflow about 20 minutes, and it is the formula that is under test. It renders the formula against the files with a `file://` URL base (which Homebrew accepts), puts it in a scratch tap (`brew tap-new fil-check/tap`; Homebrew no longer installs a formula from a bare file), then runs `brew install --formula`, `brew test` and `brew audit --strict` on Apple silicon (`macos-15`) and Intel (`macos-15-intel`), and removes the tap. `--online` is not run: it checks the URL, the homepage and the version against the network, and the dry run's version has no release at that URL.
- **First run found three audit failures,** fixed in the template: a `version` line redundant with the one scanned from the URL, `url` and `sha256` inside `on_macos` (Homebrew allows only a few directives there: the universal macOS archive is now the formula's own `url`, and `on_linux` overrides it), and two lines over 118 columns. Then `url` before `license`, and empty man-page and doc lists skipped (Homebrew warns; the dry run's archive has no man pages yet). Green on both architectures: run 42249513101 against dry run 41899619926. A release version whose archive name Homebrew cannot scan (a pre-release such as `0.1.0-rc.1`) would need `version` back; `brew audit` says so.

## 7. fil's apt and dnf repositories (from the release after 0.3.0)

**Decided (owner, 2026-11-11, D5):** fil serves its own signed apt and dnf repositories on the project site. They hold the release's own `.deb` and `.rpm` files, nothing rebuilt, and are signed with the package key (`docs/m4/release.md` §10.4) on the owner's Mac, like the rpms: no key in CI.

**The command, after the release is published:** `tests/release/just.sh release-repos X.Y.Z` (`tests/release/repos.sh`, an owner command of `tests/release/release.just`; it runs `entry-check.sh` first). It is a separate command, not an eighteenth step of `tests/release/just.sh release`: it publishes nothing (the site is another repository, which the release must not write), it needs only the verified files and the package key, it can be run again at any time (a new site, a key renewal) without touching a finished release's state, and leaving `release.sh`'s seventeen detected steps alone keeps the release's resume logic unchanged. Run it after `finish`, with the keys unlocked (`tests/release/just.sh release-keys unlock --need gpg`; `finish` forgets them, so unlock again):

1. **The inputs** are `target/release-verify/X.Y.Z/files/`, as `release-verify` left them: `target/release-verify/X.Y.Z/verified` must say they were verified with the signature (`presign=0`) and name the `SHA256SUMS` that is there, every file must match it, and both rpms must carry the package key's signature. Anything else stops the command before it writes.
2. **The trees** (`tests/release/repos.py`, Python's standard library, nothing run from the packages):
   - `apt/`: `pool/main/f/fil/` holds the two `.deb`; `dists/stable/main/binary-{amd64,arm64}/Packages` (and `.gz`) each list one package with its size and SHA-256; `dists/stable/Release` lists those indexes with their SHA-256.
   - `rpm/`: the two `.rpm`; `repodata/` holds `primary`, `filelists` and `other` (gzip, named by their SHA-256) and `repomd.xml`, which lists them with their SHA-256; `primary` binds each rpm by its SHA-256. `fil.repo` is the dnf configuration users download (`gpgcheck=1`, `repo_gpgcheck=1`).
   - Each run makes a complete repository of that one release: older versions are not kept, so a client always gets the latest.
3. **The signatures**, by gpg with the key of `.github/package-signing-key.asc`: `dists/stable/InRelease` (clearsigned) and `Release.gpg` (detached), and `repodata/repomd.xml.asc` (detached). Each is verified with the public key alone in a scratch keyring (and `InRelease` must carry exactly `Release`), and the public key is copied into both trees as `fil-package-key.asc`. One signature over the top index covers every byte a client installs, because each index binds the next by digest.
4. **The install test** (Docker; `--no-install-test` skips it): in the pinned Debian 13 and Fedora 45 images of `install-packages.sh`, with no network, apt and dnf install `fil` from the trees as `file://` repositories with every signature check on, `fil --version` must name X.Y.Z, and the package is removed. It tests this machine's architecture (`--arch all` for both, where Docker can run the other).

Checked when it was built (2026-11-14) on the published 0.3.0 packages, re-signed with a throwaway key: both trees installed in Debian 13 (apt 3, `sqv`) and Fedora 45 (dnf5) on arm64; a changed `Packages` (hash mismatch), a changed `InRelease` ("Message has been manipulated") and a changed `repomd.xml` (the repository is skipped) were each refused. `just release-test` covers the command on synthetic packages with a throwaway gpg key (the refusals, the digests in every index, the signatures), without Docker.

**No `Valid-Until` (decided in the PR #7 review, 2026-11-14).** apt's `Release` carries no `Valid-Until`, and dnf's metadata has no expiry either. The trade-off: with an expiry (say 120 days), someone who controls the site (the Pages account or the site's repository) could not keep serving an older, correctly signed tree for long, but the owner would have to re-sign the indexes on the Mac before every expiry, and a missed renewal breaks `apt update` for every user. Without it, such a person can freeze users at an older release indefinitely (apt and dnf do not downgrade, so they keep what they have; new installs get the old version), though never make them install anything the package key did not sign. Accepted, as by many third-party repositories; revisit if the re-signing can be automated without putting the key in CI.

**The package key's renewal.** `.github/package-signing-key.asc` expires on 2028-11-08. Well before then (aim: 2028-08), the owner extends it (`gpg --quick-set-expire FPR 2y`, `docs/m4/release.md` §10.4), sends the re-exported public key in a PR, and runs `release-repos` again so that both trees serve the extended key as `fil-package-key.asc`. The fingerprint does not change. apt users hold the copy they downloaded into `/etc/apt/keyrings/fil.asc`, which keeps its old expiry: they re-run the one `curl` line of `docs/user/install.md`, which says so, and the release notes of the first release after the extension repeat it. dnf imports the key from `gpgkey=` and asks to import the extended one when the old one has expired. A `fil-archive-keyring` package that apt upgrades like any other is the later alternative if users ask.

**The hand-off to the site** (a task in the site's repository, `website/fil-site`, not here): the command prints where the trees are, `target/release-verify/X.Y.Z/repos/`. Copy

| From | To | Served at |
|---|---|---|
| `target/release-verify/X.Y.Z/repos/apt/` (all of it) | the site's `/apt/` | `https://fil.anthonywertz.com/apt/` |
| `target/release-verify/X.Y.Z/repos/rpm/` (all of it) | the site's `/rpm/` | `https://fil.anthonywertz.com/rpm/` |

replacing what was there (a file the new tree lacks, such as the last release's packages or old `repodata/*.xml.gz`, goes). The site must serve the files byte for byte (no rewriting, minifying or compressing of `.gz`, `.xml` or `.asc`) and over HTTPS only; `--base-url` changes the address written into `fil.repo` if the site moves. Upload order matters for a client that updates mid-copy: copy the packages and the indexes first and `InRelease`, `Release`, `Release.gpg` and `repodata/repomd.xml` with its `.asc` last; a client that sees the old top index until then installs the old release. GitHub Pages limits a file to 100 MB, which the packages (about 14 MB each) are far below.

## 8. The installer (from the release after 0.3.0)

**Decided (owner, 2026-11-11, D5):** a `curl | sh` installer that lives in the immutable release assets and on the site, and only downloads, verifies `SHA256SUMS` against the pinned release key (`ssh-keygen -Y verify`) and copies `fil` into `~/.local/bin`, with no root. The docs show the one-liner and the download-read-run form (`docs/user/install.md`).

- **The script** is `packaging/install.sh` (owned, with the other packaging templates: it carries the release key, a trust anchor, so a change to it needs the code owner), published in every release as `fil-install.sh`: `package.sh` copies it byte for byte, it is the tenth file `SHA256SUMS` lists (`docs/m4/release.md` §4.1), the release key's signature covers it, CI attests it and `release-verify`'s rebuild reproduces it. Not a rendered template: the script holds no version, so the copy in a release is the tree's file at the tag.
- **What it does:** POSIX sh (checked with `dash -n` and shellcheck), no root. It checks its tools first (curl for an `https://` URL, `ssh-keygen` with `-Y`, which needs OpenSSH 8.1 or later and is named as such when missing, a SHA-256 tool, tar, gzip). It finds the release (`latest/download/`, or `download/vX.Y.Z/` with `--version`), downloads `SHA256SUMS` and `SHA256SUMS.sig` with curl (`--proto =https --proto-redir =https --tlsv1.2`: no plain HTTP, not even on a redirect; there is no wget fallback, because GNU wget's `--https-only` does not stop a redirect to HTTP and busybox wget lacks the option) and verifies the signature with `ssh-keygen -Y verify -I release -n fil-release` against the key in `FIL_RELEASE_SIGNERS`, the `fil-release` lines of `.github/release-signers`, as `verify.sh` does. Then it takes this machine's archive (`uname -s`/`-m`: the two Linux archives, or the universal macOS one, never the `.ci` copy) from the verified list, downloads it from that release's own `download/vVERSION/` (never `latest` a second time, which could have moved), checks its SHA-256 and unpacks it in a temporary directory. It installs `bin/fil` into `~/.local/bin` (`--dir`, `FIL_INSTALL_DIR`) and `libexec/fil/remote/` into `../libexec/fil/remote` from there, both resolved physically (`pwd -P`), because the client looks for its bundle beside its canonical path: a symbolically linked `~/.local/bin` gets the bundle beside the directory it points to. Both are staged under `mktemp` names in their directories and renamed into place, the bundle first; if a rename fails the old bundle is put back, so any failure leaves nothing installed. It refuses a symbolic link or anything but a regular file at the target and a URL other than `https://` (or `file://`, for a local copy laid out like GitHub's). It runs nothing it downloaded but the installed `fil --version`, and everything is inside a function called on the last line, so a download cut short runs nothing.
- **The pinned key** must equal the `fil-release` lines of `.github/release-signers`: `release-check` fails a release whose installer pins anything else (and `just release-test` the tree). It also requires exactly one `FIL_RELEASE_SIGNERS=` and one `FIL_RELEASE_PRINCIPAL=` assignment, every pinned line to name that principal first (what `ssh-keygen -I` matches), the `fil-release` namespace, and the one verify call to read exactly those (`installer_pin_problems` in `common.sh`). A key rotation changes both files in one PR. An installer from an older release then refuses a newer release signed with the new key, and says to get the current installer.
- **On the site:** the site can serve the latest release's `fil-install.sh` at a short address (for example `https://fil.anthonywertz.com/install.sh`), copied from the published release, byte for byte. The script verifies what it installs either way; the site copy is a convenience, and the docs keep the GitHub release URL as the primary one.
- **Tested** by `just release-test` offline: a fake release directory (`file://`) signed with a throwaway key, against a copy of the script that differs from the real one only in that key; it installs, and refuses a signature by another key, a changed `SHA256SUMS`, a changed archive, a missing signature, two matching archives, a version that does not match, a non-HTTPS URL, a missing curl, an ssh-keygen without `-Y`, a symbolic link or a directory at the target; a symbolically linked install directory gets the bundle where fil looks; and the archive comes from the release's own directory.

## 9. The owner's submissions: AUR and nixpkgs

Both need the owner's own accounts (D5), so they are prepared here and submitted by the owner. Neither depends on the installer or the repositories: the AUR package installs from the release's Linux archives (by the checksums in the verified `SHA256SUMS`, where `fil-install.sh` is one more line the renderer ignores), and Nix builds from the tagged source.

**AUR (`fil-shell-bin`)**, once, then for each release:

1. Once: make an AUR account (registration was closed to new accounts when PKG was built, §6), add an SSH public key to it, and add `Host aur.archlinux.org` with that key (`IdentityFile`, `User aur`) to `~/.ssh/config`.
2. Once: `git clone ssh://aur@aur.archlinux.org/fil-shell-bin.git ~/dev/aur-fil-shell-bin` (an empty repository: cloning a name that does not exist creates it on the first push).
3. Each release, after `finish`: `just aur-pkgbuild X.Y.Z` (from the verified `target/release-verify/X.Y.Z/files/SHA256SUMS`), then copy `target/packaging/aur/PKGBUILD` and `.SRCINFO` into the clone.
4. Check it on an Arch machine or container: `makepkg -si` in the clone (it downloads the archive and checks the sums), then `fil --version`; `namcap PKGBUILD` and `namcap fil-shell-bin-*.pkg.tar.zst` for lint.
5. `git add PKGBUILD .SRCINFO && git commit -S -m "fil X.Y.Z" && git push` (the AUR accepts only `master`; the first push of the repository publishes the package).

**nixpkgs (`fil-shell`)**, once (later versions are usually bumped by nixpkgs' update bot, or by the same steps with a new version and hashes):

1. Wait until nixpkgs' `rustc` is at least the workspace's `rust-version` (`docs/m4/nixpkgs-pr.md`, "Before opening it").
2. Fork `NixOS/nixpkgs` on the owner's GitHub account, and add the maintainer entry to `maintainers/maintainer-list.nix` (the GitHub handle and a contact of the owner's choosing) in its own commit.
3. Add `pkgs/by-name/fi/fil-shell/package.nix` from `docs/m4/nixpkgs-pr.md`, with the release's version; build once with `lib.fakeHash` for `hash` and `cargoHash`, and copy the real hashes from the two errors.
4. `nix-build -A fil-shell`, `./result/bin/fil --version`, and `nixpkgs-review wip`; then open the PR against `master` with the title `fil-shell: init at X.Y.Z` and the checklist nixpkgs' template asks for.
5. The flake in this repository (§5) stays the way to install a version before nixpkgs has it.

Checked for 1.0's new files (2026-11-14): `packaging/render.sh aur` and `brew` render from a `SHA256SUMS` that lists `fil-install.sh` (the self-test's render cases); the flake builds from `cleanSource ./.`, which the installer and the repository tooling do not change (it was not rebuilt: there is no Nix on the Mac).
